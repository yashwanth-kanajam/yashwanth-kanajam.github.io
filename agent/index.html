Claims Quality Agent

Claims-validation checks made available through an MCP server, then tested to see whether an agent running them beats a plain script. It didn't.

Problem

Teams are starting to let LLM agents write their data-quality reports. The worry is the numbers. If the model miscounts or invents a figure, the report still reads fine, and someone downstream acts on a count nobody checked. Before trusting an agent with that job, it was worth asking whether it does the job any better than a script running the same checks.

What I did

Took the five SQL checks from the claims quality project and put them behind an MCP server as read-only tools, using that project's code as-is. Built an agent on top: the model picks which checks to run and writes a short summary, but it never touches the numbers. Code fills in every figure in the report straight from the check results, and any summary that quotes a number the checks didn't return gets rejected. The model never sees the claims themselves, only counts and table names.

In these runs the model was a scripted stand-in, not a live LLM.

MCP tools
ToolReturns
summarize_data_qualityRequired tables and columns, row counts, whether validation can proceed, and the number of issues each check found
detect_duplicatesExact duplicate records
check_broken_keysRows whose member, provider or claim header does not exist
check_date_sequencesDate sequences that break the rules set for this synthetic dataset, such as a service that ends before it starts
reconcile_header_to_linePayment reconciliation failures, plus claim-level payments, service-line payments, and the inflated total from summing header payments after the join

Before testing the agent, matched the tools' output against the original checks on 88 runs, with no differences. Then ran the agent and a fixed script that calls all five checks in order on the same 15 cases: clean data, each type of defect, missing tables and columns, tool errors, limits set too low, and instructions hidden inside data values.

Result

The agent did not beat the no-model baseline. Both passed all 15 cases. The agent made fewer tool calls, 63 to 76, but only because of rules written into it: it stops after one call when the data is refused, and stops early when the cost cap is set too low. No model judgment was involved. The script cost nothing to run, while the agent's simulated model cost came to $0.2071. With a fixed five-table input, the script does the same job without a model.

Guardrails

Limits that apply on every run.

GuardrailRule
Model cost$0.50 per run (simulated). Before each call, its worst-case cost has to fit in what's left of the budget, or the call isn't made.
Tool calls12 per run, with retries counted.
Retries2 per call.
RefusalIf required data is missing or can't be read, the run stops and doesn't retry.
Source filesHashed before and after every run. If anything changed, the run fails. This flags the change; it doesn't block it.
Unknown toolsRejected before they reach the server.
Unsupported numbersAny summary quoting a number no tool returned is rejected.

Limitations

No live LLM was run, so nothing here shows how a real model would behave. The hidden-instruction test only shows that the planted text never reached the model, not that a model would ignore it. The number check catches made-up numbers, but not a real number attached to the wrong label. Equal pass rates also say nothing about speed, how useful the summaries are, or inputs outside these 15 cases. All data is synthetic, and this isn't a production system.
